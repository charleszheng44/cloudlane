# Independent consumer-protocol review — v2

**Verdict: credible consumer-only direction; revise the protocol contract before calling the design implementation-ready.** QR login and direct consumer playback have concrete source support without developer registration or partner onboarding. The proposed proof phase is appropriate. Full authenticated operation and complete feature parity remain unverified, as the design itself correctly states.

Reviewed DESIGN.md, COVERAGE.md, preview.html, the pinned module inventory, selected Node and Rust implementation files, and the upstream Together issue linked by the Node documentation. No account was accessed, credentials read, login attempted, dependencies installed, or service mutations performed. These findings concern the design and reference-port risks, not bugs demonstrated in a production client. No prior proposals, archived designs, or other reviews were consulted.

1. **High — Explicitly bind transport state and open media to the account generation.** [DESIGN.md:65](/home/zc/Work/netease-native-design/DESIGN.md:65) gives sound account/model isolation requirements, but the port needs a more concrete boundary than cancellation and stale model-result rejection. The selected upstream transport keeps XEAPI session ID/key in module globals ([request.js:133](/home/zc/Work/netease-native-evaluation/sources/node-api/util/request.js:133)) and mutates them from response headers before delivering decoded results ([request.js:469](/home/zc/Work/netease-native-evaluation/sources/node-api/util/request.js:469)). An old request could therefore affect a new account even when its body is discarded if that pattern is carried into C++. Already-open libmpv URLs and buffered protected audio also outlive a canceled provider request. **Fix:** specify an account/session-owned cookie jar, protocol session state and upload credentials; guard header side effects with the same generation check as bodies. On switch/logout, invalidate the playback generation, stop/release account-bound media, and require resolution under the new account before resuming it. Add delayed Set-Cookie/XEAPI-header and already-buffered paid-track switch cases to the existing isolation acceptance test.

2. **Medium — Playlist privacy editing is broader than the cited consumer operation.** The unified create/edit form includes privacy ([DESIGN.md:34](/home/zc/Work/netease-native-design/DESIGN.md:34)), and the ledger labels it Source-backed. Creation supports public/private, but [playlist_privacy.js:5](/home/zc/Work/netease-native-evaluation/sources/node-api/module/playlist_privacy.js:5) hardcodes `privacy: 0`; the upstream documentation describes making a private playlist public ([home.md:4017](/home/zc/Work/netease-native-evaluation/sources/node-api/public/docs/home.md:4017)). This does not establish changing an existing public playlist to private. **Fix:** distinguish creation privacy from supported edit transitions, show the existing value accurately, and mark the reverse transition Investigate until its consumer contract is established. Do not let selecting “only me” produce a success state for a still-public playlist. This is an evidence gap, not a claim that the reverse operation is impossible.

3. **Medium — Together lacks a grounded receive/synchronization contract.** [COVERAGE.md:34](/home/zc/Work/netease-native-design/COVERAGE.md:34) covers both participant roles, drift/reconnect and leave/end, but its evidence mostly names room lifecycle and outbound command modules. [listentogether_play_command.js:7](/home/zc/Work/netease-native-evaluation/sources/node-api/module/listentogether_play_command.js:7) requires sequence-bearing commands; [listentogether_sync_list_command.js:7](/home/zc/Work/netease-native-evaluation/sources/node-api/module/listentogether_sync_list_command.js:7) separately versions playlist state. The bundled host example fetches an initial list and sends controls; it does not establish ongoing receipt and application of remote playback updates. The linked [upstream investigation](https://github.com/Binaryify/NeteaseCloudMusicApi/issues/1676) also presents partial protocol observations. **Fix:** mark the receiving/sync and guest-leave contracts Investigate, identify the state/event source and its version/timing fields, and define recovery from missed updates. Require a two-client proof that each participant resolves media with their own entitlement, including unequal rights, remote seeks, reconnect and leaving without accidentally ending another participant’s session. A general “sync status” UI is insufficient evidence for this feature.

4. **Medium — The rights evidence must exclude lossy upstream convenience decoders.** The availability rules in [DESIGN.md:67](/home/zc/Work/netease-native-design/DESIGN.md:67) are appropriately cautious, but [COVERAGE.md:20](/home/zc/Work/netease-native-design/COVERAGE.md:20) cites `check_music` as rights evidence. [check_music.js:14](/home/zc/Work/netease-native-evaluation/sources/node-api/module/check_music.js:14) reduces the response to a boolean and labels every negative case “no copyright,” losing precisely the distinction the product promises. The Rust behavioral reference likewise skips null URLs and retains no preview/expiry information in its song URL model ([model.rs:227](/home/zc/Work/netease-native-evaluation/sources/rust-api/src/model.rs:227)). **Fix:** explicitly base the native rights decoder on preserved raw URL/detail/privilege responses, not these convenience outputs. Add a small field-to-state contract with Unknown for unsupported reasons; retain expiry, actual format/level and trial boundaries independently. Include a non-null trial URL and a negative availability result with no reliable restriction reason in protocol-proof fixtures.

5. **Medium — Playlist import needs its actual asynchronous workflow and source names.** The playlist-edit row cites `playlist_import`, which is absent from the pinned module inventory. The available implementation creates an import task ([playlist_import_name_task_create.js:57](/home/zc/Work/netease-native-evaluation/sources/node-api/module/playlist_import_name_task_create.js:57)); completion is queried separately via [playlist_import_task_status.js:3](/home/zc/Work/netease-native-evaluation/sources/node-api/module/playlist_import_task_status.js:3). The design names import but specifies task workflows only for cloud/uploads/downloads. **Fix:** cite the two real modules and describe task creation, persisted task identity, status polling, partial/unmatched outcomes and final library reconciliation. Treat task acceptance separately from imported-library success; an ambiguous create timeout must not blindly create another import task. Keep the workflow under Library so it does not add another navigation destination.

**Strengths:** The QR modules use ordinary consumer key/check routes and return account cookies, while identity is verified separately; no developer credential is required by this inspected flow. The design clearly separates source existence, prototype interaction and live proof. Secret Service/session-only fallback, origin-limited authentication, omission of alternative-source unlocking, and evidence-based availability are strong choices. Download permission is correctly separated from streaming access, and protected offline playback is explicitly gated on entitlement and native-playback proof. Keeping podcast authoring, identification and broader purchase categories as visible investigations avoids false parity claims. The compact native Qt architecture does not depend on exposing the community Node server or adding setup burden to the consumer login path.
